# Протокол синхронизации точка ↔ room server

LoRa здесь — транспорт синхронизации, не канал для людей. Пользователи сидят в wifi
companion-точки (для них это обычный фестивальный wifi с локальным сервером — от
«большого» не отличить); LoRa несёт только дифы.

Профиль трафика:

- **вверх (точка → сервер)**: объявления, размещённые пользователями на этой точке;
- **вниз (сервер → точки, широковещательно)**: дифы расписания, объявления и
  сообщения администрации — один и тот же диф сервера принимают все точки
  (дедупликация по `(node_id=сервер, seq)` это уже покрывает).

## Бюджет эфира (SF9, BW62.5, CR5 — движок v2)

| размер пакета | время в эфире |
|---|---|
| 60 Б | 739 мс |
| 200 Б | 2009 мс |

Утилизация канала с CSMA/CAD MeshCore и структурными скрытыми терминалами ≈ **0.35**
(non-persistent CSMA по Клейнроку–Тобаги ×0.55; не 18% чистой ALOHA — см. docs/audit.md,
гипотеза 11). Худший маршрут — 2 хопа (КИНОБАР через ГРЯДУ), т.е. каждый его пакет
занимает эфир дважды:

```
ёмкость ≈ 0.35 / (0.739 с × 2 хопа) ≈ 14 пакетов 60 Б в минуту на всю сеть
        ≈ 0.35 / (2.009 с × 2 хопа) ≈ 5.2 пакета 200 Б в минуту
```

## Формат дифа (бинарный, ≤200 Б всего пакета)

Заголовок 12 Б + записи. Всё little-endian, полезная нагрузка — до 180 Б.

```
диф:    ver(1) | node_id(1) | seq(2) | base_ts(4) | n_entries(1) | flags(1) | crc16(2)
запись: type(1) | id(2) | dt(2, сек от base_ts) | len(1) | payload(len)
```

- `type`: 1 объявление точки, 2 правка, 3 удаление, 4 сервисное (статус точки),
  5 элемент расписания, 6 сообщение администрации (5 и 6 — только от сервера)
- `id`: идентификатор поста в пространстве узла (`node_id:id` глобально уникален)
- Текст — UTF-8, длинный пост режется на несколько записей с одним `id` и
  порядковым номером в первом байте payload
- `seq` — сквозной номер дифа узла, монотонный; дедупликация по `(node_id, seq)`

## Расписание обменов

Бюджет эфира: 0.35 утилизации ≈ **21 с эфира в минуту** на всю сеть; пакет 200 Б —
2.0 с, через репитер — ×2.

**Базовый план (4 companion):**

- пуш точки раз в **90 с** (только при наличии новых данных, джиттер ±15 с):
  ≤4×0.67×2.0×1.2 хопа ≈ 6.4 с/мин;
- широковещательный пуш сервера (расписание/объявления/сообщения администрации)
  раз в **60 с** при наличии новых: ≈ 4 с/мин с ретрансляцией ГРЯДЫ;
- итого ≈ 10 с/мин из 21 — двукратный запас на ретраи и adverts.

**Полный wifi-план (13 companion, docs/deploy/mesh-plan-full-wifi.json):**

- пуш точки раз в **180 с**: 13×0.33×2.0×1.2 ≈ 10.4 с/мин;
- пуш сервера раз в **90 с**: ≈ 2.7 с/мин;
- итого ≈ 13 с/мин из 21. Быстрее не разгонять: 90-секундный период точек уже
  упирается в потолок (≈21 с/мин). Объявления обычно < 200 Б — фактический расход ниже.

- **Ретрай**: нет подтверждения — повтор через 8 с, дальше экспоненциально
  (16, 32, 64 с) до успеха, но не чаще пуш-окна.

## Разрыв и догон

1. Точка хранит свой журнал дифов и `last_seq` каждого соседа.
2. После восстановления линка точка шлёт `HELLO {node_id, my_seq, known: [(id, seq)...]}`
   (одна 4-я запись, влезает в 60 Б).
3. Сервер отвечает пачкой недостающих дифов, по одному пакету на обмен, начиная
   с самых свежих (свежее — ценнее на фестивале).
4. Журнал сервера — 48 ч; дыры старше просто не догоняются (принятое решение,
   не баг: лента живёт «сейчас»).
5. Часы: `base_ts` проставляет сервер при приёме; точки живут на дельтах, поэтому
   уход RTC на точке не ломает порядок.

## Отказы

- Пропала ГРЯДА → КИНОБАР копит дифы локально (wifi живёт), догоняет по п.2–3.
- Пропал room server → все точки работают локально (своя лента видна), сеть
  догоняет ленту после его возврата. Room server держать на ИБП.
- Подмена/мусор: пакет без валидного crc16 и известного `node_id` из таблицы
  ключей — молча в мусор.
